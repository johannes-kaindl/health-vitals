# Slice 3b — Internationalisierung (DE/EN)

**Datum:** 2026-07-23
**Plugin:** Health Vitals (Repo `apple-health`)
**Status:** Design bestätigt, bereit für Plan

## Ziel

Das heute deutschsprachige Dashboard zweisprachig machen (DE/EN), damit das Store-Plugin
über den deutschsprachigen Raum hinaus nutzbar ist. Die Sprache folgt automatisch Obsidians
UI-Locale; kein Setting, keine Sprachumschaltung zur Laufzeit.

## Leitentscheidung: Kanon vor Neubau (PROF-OBS-07)

Die i18n-Engine ist im Ökosystem **bereits geregelt** — `obsidian-kit/src/pure/i18n.ts`
(`pickLang`/`setLang`/`getLang`/`defineStrings`/`t`), Consumer u.a. vault-crews,
image-to-markdown, local-image-generator (vendored). Wir **übernehmen** diesen Standard
verbatim statt eine eigene Mechanik zu entwerfen. Damit sind zwei Fragen vorentschieden:

- **Sprachwahl:** `setLang(pickLang(getLanguage()))` einmalig im `onload`, EN kanonisch + Fallback.
- **Lang-Threading:** **modul-global** (`setLang`/`getLang`/`t`), *nicht* als expliziter
  Parameter durch Core-Signaturen. Das ist der etablierte Standard; Core bleibt trotzdem
  pure (kein obsidian-Import), Tests setzen `setLang()` vor Assertions.

Bewusst **nicht** genutzt: das `detectLang`-Muster (localStorage, kuro-gamification) — `pickLang`
liegt schon im Kit und ist für `getLanguage()`-Output gedacht. Wir triggern damit die
`detectLang`-Kit-Promotion nicht (Registry-Vermerk beim Abschluss).

## Architektur

### 1. Engine (vendored)

- `src/vendor/kit/i18n.ts` — verbatim-Kopie von `obsidian-kit/src/pure/i18n.ts`. Pure
  (kein obsidian-/DOM-Import). Exporte: `type Lang`, `pickLang`, `setLang`, `getLang`,
  `defineStrings`, `t`. `t(key, ...args)` mit `{0}`/`{1}`-Substitution; Fallback
  `currentLang → en → key`.
- Zusatzhelfer im Plugin (nicht Kit): `localeTag(): string` → `getLang() === "de" ? "de-DE" : "en-US"`
  für `toLocaleString`/`localeCompare`. Lebt in `src/i18n/strings.ts` (nutzt Kit-`getLang`).

### 2. Detektion & Registrierung (obsidian-Schicht)

In `src/main.ts onload`, **vor** `addCommand`/`addRibbonIcon`/`registerView`:

```ts
setLang(pickLang(safeGetLanguage()));  // safeGetLanguage: try { getLanguage() } catch { null }
registerI18n();                         // ruft defineStrings({ en: EN, de: DE })
```

`safeGetLanguage()` folgt dem etablierten Muster (epub-exporter, image-to-markdown):
`try { return getLanguage(); } catch { return null; }`. `pickLang(null)` → `"en"`.

### 3. Strings (`src/i18n/strings.ts`, plugin-eigen)

`EN`/`DE` als `Record<string, string>`; `registerI18n()` ruft `defineStrings`. Namespaces:

| Namespace | Inhalt | Quelle heute |
|-----------|--------|--------------|
| `cmd.*` | Command-Name(n) | `main.ts:23` „Dashboard öffnen" |
| `view.*` | View-Titel, Tab-Labels, Ribbon-Tooltip | `dashboard-view.ts:22-24,47`, `main.ts:26` |
| `range.*` | Range-Preset-Labels | `detail.ts:9` (`1M/3M/1J/Alles`) |
| `category.*` | Kategorie-Anzeigenamen (6) | `types.ts:3` |
| `metric.*` | Metrik-Namen (25) | `metric-catalog.ts` |
| `workout.*` | Workout-Typ-Namen (18) | `workout-catalog.ts` |
| `import.*` | Import-Status/Buttons/Anleitung/Zähler | `tabs/import.ts` |
| `overview.*` | Übersichts-Labels, Kategorie-Zähler | `tabs/overview.ts` |
| `workouts.*` | „Workouts pro Monat" u.a. | `tabs/workouts.ts:20` |
| `empty.*` | Leerzustände | `detail.ts:17,36` |
| `a11y.*` | aria-Labels | `overview.ts:47,54` |
| `error.*` | Fehlermeldungen | `health-source.ts:76` |

**Key-Paritäts-Invariante:** EN und DE haben denselben Keyset. Test nagelt das fest.

### 4. `Category` → `CategoryKey` entkoppeln (Kern der Arbeit)

Heute sind die deutschen Literale gleichzeitig **Identität** (Grouping, `CATEGORY_ORDER`,
`<details>`-`expanded`-Set) **und Anzeigetext**. Das wird gespalten:

- `metric-catalog.ts` (dort ist `Category` heute definiert, `types.ts` re-exportiert nichts
  davon): `Category` → neutrale Keys
  `"activity" | "heart" | "body" | "sleep" | "nutrition" | "other"`.
- `metric-catalog.ts`: `CatalogEntry` trägt `category: Category` (jetzt Key) + optional
  `chartKind`; **`name` entfällt** aus den Einträgen. `describeMetric(id, policy)` liefert
  `name: t("metric." + id)` (bzw. Fallback), `category` = Key. Modul-global, **kein neuer
  Parameter**. `fallbackName(id)` bleibt sprachneutral (Prefix-Strip + CamelCase-Split) und
  gilt für unbekannte Identifier in beiden Sprachen.
- `view-model.ts`: `CATEGORY_ORDER: Category[]` bleibt keybasiert (Reihenfolge unverändert).
  Sektion trägt `categoryKey` (Identität) + `categoryLabel = t("category." + key)` (Anzeige).
  `localeCompare(a.name, b.name, "de")` → `localeCompare(..., localeTag())`.
- `overview.ts`: `expanded`-Set nutzt `categoryKey` (stabil, sprachunabhängig); `<summary>`
  zeigt `${categoryLabel} (${n})` via `t("overview.categoryCount", label, n)` oder direkt.

### 5. `workout-catalog.ts`

`CATALOG` verliert die Namen; `workoutTypeName(type)` → `t("workout." + type)`, Fallback
(Prefix-Strip + CamelCase) bleibt. Modul-global.

### 6. `RangeKey` sprachneutral

`rollup.ts`: `RangeKey = "1M" | "3M" | "1Y" | "all"` (`1J` → `1Y`). Alle `case "1J"`
→ `case "1Y"`. `detail.ts` `RANGE_LABEL` entfällt → `t("range." + key)`.

### 7. Locale-gekoppelte Formatierung

- `format.ts`: `toLocaleString("de-DE")` → `toLocaleString(localeTag())`.
- `import.ts:26`: `toLocaleString("de-DE")` → `localeTag()`.
- `view-model.ts`: `localeCompare(..., "de")` → `localeTag()`.

## Testing

- **Neu:** `src/vendor/kit/i18n.ts` bekommt keinen eigenen Test (verbatim Kit-Kopie, im Kit getestet).
- **Key-Parität:** EN- und DE-Keyset identisch (`Object.keys` Vergleich).
- **Katalog-Übersetzung:** `describeMetric`/`workoutTypeName` liefern DE unter `setLang("de")`,
  EN unter `setLang("en")`, Fallback-Name für unbekannten Identifier in beiden.
- **Category-Key-Stabilität:** Gruppierung/`CATEGORY_ORDER`/`expanded`-Set identifizieren über
  Key, unabhängig von der Sprache (Sprachwechsel ändert nur Labels, nicht die Identität).
- **RangeKey-Rename:** `resolveRange("1Y", …)` verhält sich wie vormals `"1J"`.
- **Bestehende Core-Tests:** setzen `setLang("de")` im Setup, um heutige Assertions
  (deutsche Namen) grün zu halten — oder werden auf Keys/beide Sprachen umgestellt.
- **obsidian-Layer:** `getLanguage()` gemockt; Detektion `pickLang` in beiden Richtungen.

## YAGNI / Nicht-Ziele

- Kein Settings-Tab, keine Laufzeit-Sprachumschaltung, kein Reaktiv-Re-Render.
- Keine dritte Sprache, keine Pluralisierung/Genus (der `{0}`-Args-Mechanismus genügt).
- Keine Änderung an CSS-Prefix (`ah-`), ViewType (`apple-health-dashboard`) oder Cache-Schema.
- Monats-/Datumsachsen bleiben numerisch (`YYYY-MM`) — deren sprachliche Aufbereitung ist
  Slice 3c, nicht hier.
